# YourSafe security hardening requirements

Purpose: Close the verified desktop/extension authorization gaps and harden local secret handling with the smallest complete implementation.

Assumptions: One Windows user and desktop vault; Chrome/Edge-compatible extension; .NET 10, WinUI 3 and strict TypeScript. Browser integration is opt-in for the current app session and starts disabled. Password and OTP releases are one-shot desktop approvals; there is no background OTP grant or automatic renewal. Existing supported vault formats and desktop sign-in/recovery workflows are preserved. Old trusted-unlock tokens require a fresh Master Password sign-in, and oversized/excessively costly input is rejected under the explicit limits below.

Current phase: security requirements, implementation and source review. The user deferred further tests, builds, UI automation and runtime qualification. The acceptance column and adversarial matrix below describe the later verification phase; they are not claims that the final code has passed those checks. Earlier checks do not qualify changes made after them.

## Final Prompt

Implement the requirements below in the current repository. Read the connected callers, tests, build and release configuration first. Preserve the existing Core/Presentation/WinUI/NativeHost boundaries and strict shared wire schemas. Reuse the platform and installed libraries. Do not introduce a policy engine, cloud service, persistent secret cache, generalized token protocol, dependency, or unrelated redesign. A request waiting on the desktop followed by one response on its original connection is sufficient.

## Security promise and threat model

Protect password, website OTP, OTP seed, recovery codes, vault key, Master Password, private metadata and clipboard contents. Assume an extension worker can be modified to bypass all its own checks; a website can replace forms and fields; clients can disconnect, replay and flood requests; lock, expiry and edits can race approval or copy.

The required promise for secret release is: **the extension receives a password or OTP only for the exact operation approved on the desktop, once, while that request, credential and unlock session remain valid.** Unlocking the vault or supplying a plausible origin is not approval. A password approval does not authorize OTP or clipboard operations.

Enabling integration permits discovery of minimal matching metadata (ID, title, username and password/OTP capability flags) without a separate prompt. The Settings toggle must disclose that behavior. Because the desktop cannot attest the claimed origin, a modified client may enumerate plausible origins within the desktop rate limit. This privacy exposure remains while integration is enabled; keep it disabled if that disclosure is unacceptable. No secret-bearing list, seed, recovery code, vault key or Master Password is included in discovery.

The extension and the destination website can read plaintext that has been deliberately delivered to them. Clipboard clearing cannot retract a paste or a previously copied value. DPAPI CurrentUser does not isolate the application from arbitrary code running as the same Windows user. Do not describe these limitations as fixed by this change. This implementation does not claim immunity to a compromised OS, same-user malware, arbitrary memory reads, screen capture, or a compromised release account.

## Required adversarial matrix

In the later verification phase, run against synthetic data and the actual desktop/NativeHost boundary, not only the official worker:

1. Integration off; unlocked vault; enumerate origin/credential IDs without approval.
2. Approve A/password; alter ID, origin, action or connection to B/OTP/copy; replay the same request.
3. Cancel, close dialog, no handler, approval exception, deadline expiry or old protocol/action.
4. Lock, logout, lock/unlock, credential edit/delete, settings change, vault/session deadline or integration disable while waiting.
5. EOF, extra frame, malformed/duplicate/unknown JSON, wrong peer executable and slow/oversized transport.
6. Parallel clients/profile/browser processes, repeated discovery, repeated prompts and multiple uses of an approval.
7. Popup focus loss versus genuine target change; reconnect/late response; worker restart; no secret cache or retry.
8. No URL, invalid URL, wrong origin/subdomain/port, dynamic form/field replacement, opacity/occlusion, cross-origin or HTTP submission.
9. Password, OTP, recovery and setup clipboard writes; after 30 seconds; transient contention; user replacement; delayed write after lock/dialog dismissal; close/crash limits.
10. Alter trusted-token dates/fingerprint/blobs, legacy token, expired token; same-user DPAPI limitation clearly stated.
11. Hash API malformed/oversized inputs, unsafe work factors and overflow, expensive concurrency/rate, loopback-only deployment.
12. Tampered `.config` KDF cost/salt/wrapped-key, oversized or growing vault/token/snapshot/transaction files, oversized backup export, and existing sign-in/recovery/reset/migration/import/transaction/protocol/release regressions.

For each case report **verified**, **partially verified**, **not run**, or **residual limitation**, with the exact command/test/source evidence. A green test encoding the old insecure policy is not acceptance: update it to the new invariant. Review the final connected change with ponytail-review and fix concrete findings before declaring completion.

Compatibility changes: browser integration starts off at each launch; each password/OTP read or OTP copy needs a new desktop approval; URL-empty items cannot autofill; browser OTP does not refresh automatically; old trusted tokens require Master Password sign-in. Visibility tracking deliberately refuses unsupported or uncertain rendering, including some filters/transparency/transforms. bcrypt input beyond 72 UTF-8 bytes and oversized/excessively costly hashes/configurations/files are rejected; existing files are not truncated or deleted to satisfy limits. Hash utility generation defaults are unchanged; inspection identifies compatible formats whose cost needs strengthening.

Resource limits: config/token/snapshot metadata is capped at 64 KiB; encrypted vault/snapshot JSON at 64 MiB; backup and Presentation import files at 10 MiB. The existing transaction journal embeds both documents as escaped JSON strings, so its format-preserving quota is `6 × (64 MiB + 64 KiB) + 1 KiB` (403,047,424 bytes). This is a finite document limit, not a promise of low peak memory at the maximum. Wrapped-key JSON is capped at 4,096 characters with a 32-byte key; nonce/tag encodings have fixed lengths. Password/passphrase inputs are capped at 4,096 characters, PBKDF2 at 1,000,000 iterations, Argon2 at 128 MiB with bounded passes/parallelism and combined work, and scrypt at 128 MiB plus a combined work limit. Existing generated vault defaults (Argon2 64 MiB/3 passes/parallelism 2 and legacy PBKDF2 600,000) remain within the bounds.

Deferred: final Core/Presentation suites, WinUI/NativeHost/API and extension builds/typecheck, browser DOM/extension E2E, actual Windows clipboard/pipe/approval cancellation and release qualification. Earlier successful checks preceded the final source edits and do not establish final-artifact acceptance. Completed implementation/source review must not be labeled as tested, signed, published or immune to credential theft.
